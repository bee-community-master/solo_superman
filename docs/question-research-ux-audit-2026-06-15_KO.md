# 질문/리서치 UX 감사 기록 - 2026-06-15

## 목적

Solo Superman을 "기획을 상세화하는 도구"로 포지셔닝할 때 핵심 루프는 질문 생성과 리서치다. 이 문서는 로컬 웹 앱을 실제로 사용하며 다음을 점검한 기록이다.

- 질문이 일반 사용자에게 쉬운 단어로 구성되는가
- 질문이 실제 기획 상세화에 필요한 판단을 묻는가
- 사용자가 답변과 리서치 결과를 넣었을 때 기획이 구체화된다는 효용을 느끼는가
- ChatGPT Deep Research handoff와 공개 웹 리서치 흐름이 실제 사용 맥락에서 충분히 믿을 만한가

## 테스트 조건

- 실행 명령: `SOLO_LOCAL_OPEN_BROWSER=0 pnpm start:local`
- 로컬 웹: `http://127.0.0.1:1420`
- Sidecar 상태: local service connected, Codex CLI account status `authenticated`, execution mode `manual_handoff`
- Live preview 상태: `SOLO_CODEX_SDK_LIVE_TURNS=1`이 꺼져 있어 기본 질문 fallback과 수동 handoff 중심으로 검증
- ChatGPT 브라우저 확인: in-app browser의 `https://chatgpt.com/` 탭은 로그인 CTA를 표시했다. 실제 Pro/Deep Research 실행까지는 검증하지 못했고, Solo Superman의 visible ChatGPT handoff와 manual import UX를 검증했다.

## 샘플 아이디어

아이디어 요약:

> 동네 자영업자가 단골 고객 예약, 대기, 쿠폰을 카카오톡처럼 쉽게 관리하는 모바일 웹 서비스

목표:

> 미용실, 네일샵, 작은 음식점 사장님이 복잡한 CRM 없이 재방문 고객을 늘릴 수 있는 서비스를 기획하고 싶다. 이번 세션에서는 첫 출시 범위, 꼭 필요한 화면, 리서치로 확인해야 할 경쟁 대안과 고객 니즈를 구체화하고 싶다.

선택한 설정:

- 프로젝트 목적: 서비스 기획 구체화
- 질문 방식: 조금 더 자세히 묻기
- 리서치 설정: Codex + 보이는 ChatGPT Deep Research

## 관찰 요약

현재 버전은 기획 상세화 도구로서 방향은 맞지만, 질문과 리서치가 사용자가 기대하는 수준의 "기획이 정리되고 있다"는 체감까지 충분히 만들지 못한다. 특히 리서치 흐름은 결과를 붙여 넣은 뒤 다음 질문과 기획 초안으로 명확히 전환되지 않아 효용이 약하게 느껴진다.

좋았던 점:

- 첫 질문은 샘플 아이디어의 도메인을 일부 반영했다. 예: "소상공인 예약/주문에서 누구를 먼저 도울까요?"
- 첫 답변 후 준비도가 `0%`에서 `34%`로 올라가고 후속 질문/리서치 작업이 생겼다.
- ChatGPT handoff는 비밀번호, cookie, API key를 요구하지 않고 사용자 소유 브라우저에서 검토하도록 설명한다.
- 리서치 import textarea는 사용자가 가져온 공개 출처 요약을 받을 수 있었다.

부족했던 점:

- 질문 생성 중 곧바로 "라이브 질문 생성이 60초 걸렸습니다" 안내가 표시되어 사용자가 기다려야 하는지, fallback을 써야 하는지 판단하기 어렵다.
- 첫 질문은 도메인에 맞지만 "소상공인 예약/주문"처럼 너무 넓은 표현으로 뭉개져, 사용자가 넣은 "미용실, 네일샵, 작은 음식점" 중 어떤 범위를 우선할지 더 선명하게 묻지 못했다.
- "다른 관점 점검 질문", "차분하게 구체화", "질문 debt", "후속 질문 여유" 같은 표현은 내부 시스템 상태에 가깝고 일반 사용자에게 효용 언어로 읽히지 않는다.
- 답변 저장 후 "저장한 답변 제출" 버튼이 비활성화되어 저장과 제출의 차이가 흐렸다. 실제로는 답변이 반영된 듯하지만 사용자는 완료 여부를 확신하기 어렵다.
- 공개 웹 리서치 시작은 `blocked`로 기록됐지만 화면에 왜 막혔는지, 사용자가 다음에 무엇을 해야 하는지 충분히 설명하지 않았다.
- ChatGPT Deep Research 프롬프트에는 빈 기획 섹션명(`Problem Target Customer JTBD / Use Case...`)이 그대로 들어가 품질 신뢰를 떨어뜨린다.
- 수동 리서치 결과를 붙여 넣은 뒤에도 "가져온 결과를 근거로 바꾸는 중" 상태가 10초 이상 유지됐고, 후속 질문/근거 품질/기획 초안이 사용자에게 뚜렷하게 갱신되지 않았다.

## 질문 품질 평가

### 쉬운 단어인가

부분적으로 그렇다. 첫 질문의 핵심 문장 자체는 쉽다. "누구를 먼저 도울까요?", "지금 어떤 방법으로 이 문제를 해결하고 있나요?"는 일반 사용자도 이해할 수 있다.

다만 주변 UI가 어렵다. "검토 상태", "영향도", "질문 진행률", "후속 질문 여유", "다른 관점 점검 질문"은 제품 내부 평가 체계처럼 보인다. 기획 상세화 도구라면 사용자가 보는 말은 "지금 정할 것", "답하면 정리되는 것", "다음으로 확인할 것"처럼 행동 중심이어야 한다.

개선 방향:

- 질문 카드의 핵심 문장만 크게 남기고 내부 분류명은 접거나 보조 정보로 낮춘다.
- "다른 관점 점검 질문" 대신 "놓치기 쉬운 확인 질문"처럼 사용자 언어로 바꾼다.
- "후속 질문 여유 61" 같은 숫자는 일반 사용자에게 의미가 없으므로 숨기거나 "아직 더 물어볼 수 있는 질문이 충분합니다"처럼 바꾼다.

### 실질적으로 필요한 질문인가

첫 질문은 필요하다. 초기 기획에서 고객군을 먼저 좁히는 것은 맞다. 선택지도 `1인 미용실/네일샵 예약 누락`, `소형 음식점 주문 확인`, `단골 재방문 관리`로 실제 판단을 요구한다.

하지만 질문의 정밀도가 부족하다. 사용자가 이미 "미용실, 네일샵, 작은 음식점"과 "재방문 고객"을 목표에 썼는데, 첫 질문은 다시 넓은 고객군 선택으로 돌아간다. 더 좋은 첫 질문은 사용자가 쓴 범위 안에서 첫 버전의 가장 위험한 판단을 바로 묻는 것이다.

더 나은 질문 예:

- "첫 버전은 1인 미용실/네일샵의 예약 누락을 먼저 줄이는 도구로 좁혀도 되나요?"
- "사장님이 지금 가장 자주 놓치는 예약 채널은 전화, 카카오톡, 인스타 DM, 네이버 예약 중 무엇인가요?"
- "첫 화면에서 반드시 보여야 할 것은 오늘 예약표, 새 문의함, 재방문 알림 대상 중 무엇인가요?"

개선 방향:

- 질문 생성 기준을 "고객군 확인"에서 "다음 화면/기능/검증이 달라지는 판단"으로 강화한다.
- 사용자가 이미 제공한 정보는 반복 질문하지 말고, 선택지를 더 좁히는 질문으로 전환한다.
- 각 질문에는 "이 답변 후 기획서에 어떤 문장이 채워지는지"를 한 줄로 보여준다.

### 기획 상세화 효용이 느껴지는가

초반에는 약하게 느껴진다. 답변 후 준비도와 후속 질문이 생기는 점은 긍정적이다. 그러나 리서치까지 포함하면 효용이 끊긴다. 사용자는 "리서치를 넣었는데 무엇이 바뀌었는지"를 바로 보지 못한다.

개선 방향:

- 답변 저장 직후 `기획 초안 변경점`을 diff처럼 보여준다.
- 리서치 import 직후 `새로 알게 된 것`, `기획에서 바뀐 판단`, `다음 질문`을 즉시 카드로 표시한다.
- "pending"이나 "근거로 바꾸는 중" 상태가 길어질 때는 예상 시간, 복구 버튼, 수동으로 계속 진행하는 선택지를 제공한다.

## 리서치 품질 평가

### ChatGPT Deep Research handoff

생성된 handoff 프롬프트는 구조가 있고 출처 요구사항도 포함한다. 그러나 다음 문제가 있었다.

- 사용자가 ChatGPT에 실제 로그인했는지 Solo Superman은 확인하지 못한다. 체크박스만으로 다음 단계가 열리며, in-app browser에서는 로그인 CTA가 보였다.
- 프롬프트가 너무 길고 일부 기획 초안이 빈 섹션명으로 들어간다.
- "이번 리서치로 좁힐 결정"이 너무 넓다. 사용자 미래, 대표 사용 케이스, 기존 대안, 막힐 상황, 대응 선택지, 한계, 다음 질문까지 한 번에 요구해 결과가 넓고 얕아질 위험이 있다.

개선 방향:

- ChatGPT 로그인 확인은 "확인했습니다" 체크박스만 두더라도, 실제 ChatGPT 탭이 로그인 화면이면 "로그인 후 돌아오세요" 경고를 보여준다.
- Deep Research 프롬프트는 한 번에 하나의 결정만 좁히게 한다. 예: "1인 미용실/네일샵 예약 누락 문제의 기존 대안과 첫 버전 차별화만 확인".
- 빈 섹션명은 제거하고, 이미 채워진 사용자 답변과 아직 비어 있는 판단을 분리해 보여준다.
- 프롬프트 미리보기 위에 "이 리서치로 결정할 것"과 "결정하지 못하는 것"을 먼저 보여준다.

### 공개 웹 리서치

테스트에서 공개 웹 리서치 시작은 `blocked`로 기록됐고, 결과 카드에는 실행이 보이지 않았다. 화면은 소스가 활성화됐다고 말하지만, 실제 시작 실패 원인이 사용자에게 설명되지 않았다.

개선 방향:

- blocked 상태는 반드시 사유를 사용자가 읽는 말로 보여준다. 예: "검색 provider가 응답하지 않았습니다", "allowlist 정책 때문에 자동 실행하지 않았습니다", "수동 import가 필요합니다".
- 실패 카드에는 `다시 시도`, `수동으로 결과 붙여넣기`, `리서치 범위 줄이기`를 같은 위치에 제공한다.
- 자동 리서치가 실패해도 ChatGPT handoff 또는 수동 import로 이어지는 안내를 한 문장으로 연결한다.

### 수동 리서치 import

수동 리서치 결과는 import됐지만, 후속 산출물이 즉시 보이지 않았다. 이 상태에서는 사용자가 "붙여 넣은 리서치가 Solo Superman 안에서 실제로 일을 했는가"를 알 수 없다.

개선 방향:

- import 직후 3개 산출물을 보장한다: `근거 요약`, `바뀐 기획 문장`, `새 후속 질문`.
- 긴 처리 중에는 skeleton 대신 "결과는 저장됨, 기획 반영 대기 중"처럼 데이터 보존 상태를 명확히 표시한다.
- 10초 이상 pending이면 "리서치 요약만 먼저 보기"와 "후속 질문 수동 생성"을 제공한다.

## 공개 리서치에서 확인한 기획 신호

짧은 공개 웹 확인 기준으로, 샘플 아이디어의 첫 포지션은 "새 예약 플랫폼"보다 "1인 미용실/네일샵의 흩어진 예약 확인과 누락 방지"가 더 설득력 있다.

근거:

- Toss Place는 네일샵/미용실 등이 전화, 카카오톡, 인스타그램 DM, 네이버 톡톡 등 여러 채널을 병행하며 예약 누락과 중복 예약이 생기는 문제를 설명한다.
- 카카오톡 예약하기와 네이버 예약은 이미 예약 생성, 확정/취소, 예약자 관리, 알림 설정 등 핵심 예약 기능을 제공한다.
- 공비서, 팅커뷰, 뷰티 CRM 계열 서비스는 예약, 고객관리, 알림톡, 회원권/선불권, 매출 관리까지 묶어 제공한다.
- 따라서 첫 버전은 플랫폼 대체보다 "사장님이 이미 쓰는 채널을 놓치지 않게 돕는 얇은 inbox/확인 도구"로 검증하는 편이 낫다.

## 우선순위별 개선 방향

### P0 - 기획 상세화 체감 회복

1. 답변 저장 후 즉시 `기획 초안 변경점`을 보여준다.
2. 리서치 import 후 `새로 알게 된 것`, `바뀐 판단`, `다음 질문`을 보장한다.
3. pending/blocked 상태에는 원인과 다음 행동을 사용자 말로 표시한다.

### P1 - 질문 품질 개선

1. 이미 사용자가 말한 정보를 반복하지 않고, 다음 화면/기능/검증이 달라지는 판단만 묻는다.
2. 첫 질문 세트는 고객군, 사용 상황, 첫 화면, 기존 대안, 첫 검증 위험을 순서대로 묻는다.
3. 질문마다 "답하면 기획서의 어느 문장이 채워지는지"를 붙인다.

### P1 - 리서치 프롬프트 개선

1. Deep Research 프롬프트는 하나의 결정으로 좁힌다.
2. 빈 기획 섹션명과 내부 상태명은 프롬프트에서 제거한다.
3. 출처 요구사항은 유지하되, 결과 형식은 `증거 -> 판단 -> 남은 질문` 순서로 받는다.

### P2 - UI 언어 정리

1. "다른 관점 점검 질문", "후속 질문 여유", "검토 상태" 같은 내부어를 사용자 행동어로 바꾼다.
2. "답변 저장"과 "저장한 답변 제출"의 차이를 없애거나 명확히 분리한다.
3. 진행률은 내부 카운트보다 "기획서에서 채워진 부분" 중심으로 보여준다.

- 각 질문은 하나의 판단만 묻고, 답변 후 채워질 기획 문장을 표시한다.
- 리서치 import 후 10초 안에 `근거 요약`, `기획 변경점`, `후속 질문`이 화면에 나타난다.
- 공개 웹 리서치 실패 시 blocked 사유와 복구 버튼이 같은 카드 안에 보인다.
