# 질문/리서치 실사용 점검

점검일: 2026-06-14

## 목적

Solo Superman을 `기획을 상세화하는 도구`로 포지셔닝할 때 핵심이 되는 질문 생성과 리서치 흐름을 실제 로컬 UI에서 사용해 보고, 현재 버전이 일반 사용자에게 기획 상세화 효용을 주는지 확인했다. 이번 문서는 개선 작업이 아니라 개선 방향 제안이다.

## 점검 환경

- 실행: `SOLO_LOCAL_OPEN_BROWSER=0 pnpm start:local`
- 로컬 URL: `http://127.0.0.1:1420`
- 검증 보조: Playwright로 로컬 UI 조작, sidecar API 응답 확인
- 선택 경로: `서비스 기획 구체화`, `조금 더 자세히 묻기`, `Codex + 읽기 전용 공개 웹 리서치`
- Deep Research 경로: `Codex + 보이는 ChatGPT Deep Research` 옵션은 확인했지만, headless 테스트 브라우저가 사용자 ChatGPT 로그인 프로필이 아니어서 "이 브라우저/프로필에서 ChatGPT에 직접 로그인했습니다" 확인을 진행하지 않았다.

## 입력한 예시 아이디어

- 아이디어: 문서와 메모를 넣으면 초보 창업자가 서비스 기획을 자세히 정리할 수 있게 도와주는 웹 도구
- 목표: 일반 사용자도 이해하기 쉬운 질문을 통해 고객, 문제, 첫 기능, 리서치할 내용이 차례로 구체화되는지 확인하고 싶다. 특히 질문이 너무 어려운 말이거나 실제 기획에 도움이 안 되는지 보고 싶다.

## 실제 관찰

### 온보딩

- 첫 화면은 한국어로 연결 상태, 목적 선택, 리서치 설정, Codex 로그인 상태를 보여준다.
- `서비스 기획 구체화`를 선택하면 질문 방식 선택지가 추가로 나타난다.
- Deep Research 옵션을 고르면 ChatGPT 로그인 확인 섹션이 나타난다. 안전한 확인 흐름은 좋지만, 사용자는 이 선택이 실제로 어떤 결과물을 더 만들어 주는지 아직 알기 어렵다.

### 질문 생성

- Codex 로그인 상태는 `로그인됨`이었지만 sidecar runtime은 `SOLO_CODEX_SDK_LIVE_TURNS=1`이 없어 live turn 실행이 비활성화되어 있었다.
- 첫 질문 생성 후 `/questions/generate` 응답은 `codex_runtime_unavailable`였고, UI는 `기본 질문으로 시작` fallback을 제안했다.
- fallback으로 시작하면 질문 4개가 생성되고 첫 질문 1개가 활성화됐다.
- 첫 질문은 `창업자 기획에서 가장 먼저 도울 실제 사용자 상황은 무엇인가요?`였다.
- 다음 후보 질문은 `창업자 기획 관련 공개 자료를 보면 어떤 사용 케이스와 기존 대안이 먼저 확인되나요?`였다.

### 질문 답변 후 변화

- 첫 질문에 답하자 질문 처리율은 20%, 계획 준비도는 34%로 올라갔다.
- 리서치 작업 1개가 생겼지만 실제 실행은 시작되지 않았다.
- 리서치 탭에서는 `공개 웹 리서치 실행 시작` 버튼이 비활성화되어 있었고, `공개 웹 리서치로 넘기기 전에 질문에 조금 더 답해주세요`라고 표시됐다.
- 문제는 현재 활성 질문이 이미 `공개 자료를 보면 무엇이 확인되나요?`였다는 점이다. 사용자는 리서치가 해줘야 할 일을 다시 질문으로 받은 셈이다.

### 리서치 경로

- 두 번째 질문에 사용자가 "잘 모르겠다. 이 부분은 Solo Superman이 공개 자료를 찾아줘야 한다"는 취지로 답변하자 `IDEMPOTENCY_CONFLICT`가 발생했다.
- UI에는 `작업 실패`가 표시되면서도 `저장한 답변 1개 제출` 상태가 남아, 답변이 저장됐는지 실패했는지 판단하기 어려웠다.
- 같은 리서치 작업을 API로 직접 시작하면 실행은 `research_insufficient`로 종료됐다.
- 실제 결과는 유의미한 공개 근거 0개, 검색 노이즈 1개, `검색어를 바꿔 공개 리포트/커뮤니티/대체재 리뷰를 확인하거나 타깃 사용자 3명에게 확인하라`는 수동 검증 안내였다.

### 로컬 verifier

- `pnpm verify:clarification-pipeline` 통과
- `pnpm verify:research-pipeline` 통과
- 다만 verifier는 fixture 기반으로 파이프라인 연결과 source trace를 확인한다. 실제 사용자가 가치 있다고 느낄 질문 품질, 쉬운 단어, 공개 웹 리서치의 유용성은 충분히 보장하지 않는다.

## 품질 판단

### 질문은 이해하기 쉬운가

부분적으로만 그렇다.

- `가장 먼저 도울 실제 사용자 상황`은 한국어 자체는 어렵지 않지만, 초보 사용자에게는 추상적이다.
- 질문 카드의 보조 문구 `질문, 리서치, 첫 화면이 서로 다른 사용자를 향할 수 있습니다`는 의도를 설명하지만, 사용자가 바로 답하기 위한 예시가 없다.
- `공개 자료를 보면 어떤 사용 케이스와 기존 대안이 먼저 확인되나요?`는 사용자가 답해야 할 질문이 아니라 리서치가 답해야 할 질문에 가깝다.
- 화면에는 `큐`, `v7`, `근거 균형`, `품질 게이트`, `route`, `projection` 성격의 언어가 남아 있어 일반 사용자에게는 내부 도구처럼 느껴질 수 있다.

### 실질적으로 필요한 질문인가

첫 질문은 필요하지만 방식이 약하다.

- 첫 고객 상황을 좁히는 질문은 기획 상세화에 필요하다.
- 그러나 현재 질문은 선택지 없이 주관식이라 초보자가 막힐 수 있다.
- 더 좋은 첫 질문은 사용자가 고를 수 있는 3-5개 후보와 `직접 입력`을 함께 주는 방식이다.
- 리서치 질문은 사용자 질문 큐에 그대로 넣기보다, 시스템이 실행할 리서치 작업으로 분리해야 한다.

### 기획 상세화 효용이 느껴지는가

아직 약하다.

- 답변 후 준비도 수치가 올라가는 것은 보이지만, 어떤 기획서 문장이 채워졌는지 화면에서 즉시 보이지 않는다.
- 리서치 작업은 생기지만 바로 실행되지 않고, 사용자는 왜 더 답해야 하는지 납득하기 어렵다.
- 리서치 결과가 `근거 부족`일 때도 다음 행동은 너무 일반적이다. 사용자는 `그래서 내 기획에서 무엇을 바꾸라는 건가`를 기대한다.

## 개선 방향

### 1. 첫 질문을 "사용자 선택 + 짧은 이유" 형태로 바꾼다

첫 질문은 주관식 하나보다 다음처럼 시작하는 편이 낫다.

- 누구를 먼저 도울까요?
- 선택지: 처음 창업하는 1인 창업자, 고객 인터뷰를 마친 예비 창업자, 이미 기획 문서가 있는 팀, 아직 잘 모르겠음, 직접 입력
- 이어서 한 줄 이유: 왜 이 사용자를 먼저 돕고 싶나요?

이렇게 하면 일반 사용자도 바로 답할 수 있고, Solo Superman은 세그먼트와 이유를 동시에 얻는다.

### 2. 질문과 리서치의 역할을 분리한다

사용자에게 물을 질문:

- 누구를 먼저 도울지
- 어떤 결과물이 나오면 "기획이 정리됐다"고 느낄지
- 첫 버전에서 꼭 필요한 기능과 빼도 되는 기능
- 지금 가진 자료와 부족한 자료

리서치가 답해야 할 질문:

- 대체재와 사용 패턴
- 공개 후기/커뮤니티에서 드러나는 불편
- 가격/결제 의향의 간접 증거
- 실패하거나 막히는 상황

`공개 자료를 보면 무엇이 확인되나요?` 같은 문장은 사용자 질문 카드가 아니라 리서치 실행 카드에 있어야 한다.

### 3. 답변 직후 "기획서가 어떻게 바뀌었는지" 보여준다

사용자가 효용을 느끼려면 답변 저장 직후 다음이 보여야 한다.

- 채워진 기획 문장: `첫 사용자는 ...`
- 아직 모호한 문장: `첫 기능 범위는 아직 ...`
- 다음 질문 이유: `이 답변 때문에 다음에는 ...를 물어봅니다`
- 리서치가 확인할 것: `공개 자료에서는 ...를 확인합니다`

준비도 34% 같은 숫자는 보조 지표로 두고, 실제 문장 변화를 앞세워야 한다.

### 4. 리서치 실행 가능 조건을 사용자 언어로 재정의한다

현재 `질문에 조금 더 답해주세요`는 너무 넓다. 대신 다음처럼 정확히 알려야 한다.

- 아직 리서치를 시작하지 않는 이유: `첫 고객 후보가 너무 넓어 검색어가 흐립니다`
- 필요한 추가 답변: `초보 창업자 / 인터뷰를 마친 창업자 / 팀 중 하나를 골라주세요`
- 바로 실행 가능한 리서치 미리보기: `선택 후 검색할 키워드 3개`

### 5. 리서치 결과는 "근거 부족"에서 끝나지 말고 검색 전략을 수정한다

현재 결과는 유의미한 근거 0개에서 수동 검증 안내로 끝난다. 기획 상세화 도구라면 다음 단계까지 만들어야 한다.

- 검색어가 왜 실패했는지 설명
- 더 좁은 검색어 3-5개 제안
- 리서치가 못 찾은 것과 사용자 인터뷰로 확인할 것을 분리
- 기획서에 반영할 임시 결론 제안: `공개 근거는 약하므로 첫 검증은 유료 결제보다 기존 문서 정리 pain 확인으로 좁힌다`

### 6. 오류 상태를 일반 사용자 행동으로 복구 가능하게 만든다

`IDEMPOTENCY_CONFLICT` 같은 내부 오류는 사용자 화면에 그대로 노출되면 안 된다. 최소한 다음 중 하나가 필요하다.

- `이미 같은 리서치 작업이 만들어졌습니다. 기존 작업으로 이동합니다.`
- `답변은 저장됐지만 리서치 작업은 이미 있어 새로 만들지 않았습니다.`
- `다시 시도` 대신 `기존 리서치 작업 보기`

### 7. 품질 verifier를 제품 품질 기준으로 확장한다

현재 verifier는 연결성 중심이다. 다음 기준을 추가해야 한다.

- 초반 질문 5개 중 4개 이상이 일반 사용자 단어로 구성될 것
- 첫 질문은 선택지 또는 예시를 포함할 것
- 리서치가 답해야 할 문장을 사용자 질문으로 내보내지 않을 것
- 답변 저장 후 기획서 문장 변화가 화면/API에 노출될 것
- live/public 리서치가 근거 0개일 때 검색어 개선안과 다음 검증 행동을 생성할 것

## 우선순위

1. 사용자 질문 큐에서 리서치가 답해야 할 질문을 제거하고, 리서치 실행 카드로 분리한다.
2. 첫 질문을 선택지 기반으로 바꾸고 `직접 입력`을 보조로 둔다.
3. 답변 저장 후 변경된 기획 문장을 즉시 보여준다.
4. 리서치 실행 비활성화 사유를 검색어/세그먼트 관점으로 구체화한다.
5. `IDEMPOTENCY_CONFLICT` 복구 UX를 추가한다.
6. 제품 품질 verifier를 추가해 fixture 통과와 사용자 효용을 분리해 측정한다.
